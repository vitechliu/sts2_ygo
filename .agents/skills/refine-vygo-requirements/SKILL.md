# 梳理 VYgo 需求

## 工作边界

只在用户显式调用 `$refine-vygo-requirements` 时使用本流程。

默认只做需求审阅、代码现状调查、方案设计、追问和规格整理，不开始实现功能。只有用户在调用中明确要求写本地文档或更新腾讯文档时，才执行对应写入；代码实现必须由后续明确请求启动。

始终使用中文交流。结果优先、问题具体，像产品与技术负责人一样推动决策，不用空泛的“请补充更多信息”。

## 1. 建立事实来源

按以下优先级处理冲突：

1. 用户本轮明确决定。
2. 实时腾讯文档中的需求与备注。
3. 当前仓库代码、`AGENTS.md`、依赖源码和构建结果。
4. 历史文档或旧任务描述。

根据输入读取必要来源：

- 用户提供腾讯文档链接或要求更新核心表格时，使用 `$manage-vygo-project` 和 `$tencent-docs`，遵守鉴权、实时表头、批量写入与回读规则。
- 用户提供本地规格时，读取 `.context/` 下相关文件。
- 需求涉及现有系统时，先检查仓库代码和只读依赖源码，确认已有能力、占位实现、复用点与真实限制。
- 修改任何仓库文件前先检查 `git status`，保留用户未提交改动。

不要为了提问而提问。能从代码、资源、表格或依赖源码查明的事实，先自行查明。

## 2. 审计需求

先给出一份简洁审计，将相关任务归入以下类别：

- **可直接执行**：需求和验收边界已经充分，AI 可以独立实现并构建验证。
- **AI 主导、用户验收**：AI 可实现，但视觉、手感、玩法平衡或游戏内行为需要用户实机确认。
- **缺少产品决定**：存在会显著改变实现方向的选择，必须追问。
- **需要人工或外部输入**：依赖美术、音频、账号、多人实测或无法由本地环境完成的操作。
- **过时或重复**：文档与代码现状冲突，或多个任务实际描述同一纵向功能。
- **长期资源任务**：图标、翻译、卡池补全等可以持续推进，但不应阻塞一个明确功能切片。

每个判断尽量附一条代码或文档证据。不要仅凭任务名称猜测工作量。

## 3. 合并与拆分

优先形成可以独立交付、独立验收的纵向切片。

满足以下条件时合并任务：

- 共用同一份持久化状态或生命周期入口。
- 共用同一套 UI，拆开后无法形成完整用户体验。
- 一项只是另一项的展示层或结算层。
- 分开实现会造成重复 API、重复迁移或重复测试。

例如：全局等级、段位、对局结算和主菜单绑定应作为一个“决斗者档案”纵向功能，而不是四套孤立任务。

满足以下条件时拆分任务：

- 可以独立发布和验收。
- 依赖不同专业输入，例如代码机制与长期图标绘制。
- 一个任务包含明确的快速收益和高风险扩展，应先切出 MVP。
- 一部分前置信息齐全，另一部分仍被产品决定阻塞。

不要为了让任务数量好看而拆分。拆分后每项都必须有独立目标、边界和验收标准。

## 4. 提问并推动决策

每轮只问 3～6 个最高杠杆问题。问题应当：

- 直接影响数据模型、交互、生命周期或验收结果。
- 给出推荐答案，并用一句话说明取舍。
- 使用互斥且易回答的选项；避免开放式长作文。
- 允许用户用一组短行或“全部按建议”完成回复。
- 明确区分“必须现在决定”和“可在实机测试后调参”。

推荐格式：

```text
档案范围：全局（建议） / 按角色
失败处理：保留大段并重置小段（建议） / 大段降级
默认演出：完整（建议） / 快速
```

如果用户没有明确里程碑：

1. 根据代码现状提出一个有辨识度但可落地的激进纵向切片。
2. 同时给出一个短周期快速收益项。
3. 说明为什么它们现在可做，以及哪些部分仍需人工测试。

如果需求复杂，不要求用户先写长文。先把问题拆成显示、状态、交互、数据、结算、兼容和验收等小块，再逐轮确认。

## 5. 维护决策账本

用户每次回答后，立即收束为：

- 已确认规则。
- 因本轮答案而取消的旧方案。
- 仍未解决的阻塞问题。
- 可以推迟到实机测试的数值或视觉参数。

纠正自己的误解时直接说明修订结果，不把误解继续扩展成需求。例如用户确认“一只怪兽只能有一个行动”后，应将多行动视为代码不变量，而不是设计多行动 UI。

避免重复询问已经确认的决定。后续建议必须与决策账本一致。

## 6. 收束为可开发规格

当阻塞性问题清零后，为每个独立任务整理以下内容：

1. 任务目标。
2. 已确认的产品规则。
3. 当前代码与资源入口。
4. 功能范围和明确非目标。
5. 数据模型、状态转换或时间线。
6. 胜利、失败、取消、异常、联机、回放和旧存档等边界情况。
7. UI 与反馈规则。
8. 向后兼容和幂等要求。
9. 可逐条验证的验收标准。
10. 建议实施顺序。
11. 构建验证与用户实机测试清单。

规格必须让新会话在不读取原聊天的情况下直接开工。不要把关键决定只留在对话总结中。

用户要求落盘时：

- 在 `.context/` 下为每个独立任务创建一个 Markdown 文件。
- 文件名使用简短的英文 kebab-case。
- 一份文件只描述一个可独立执行的任务。
- 引用真实仓库路径与只读依赖入口。
- 如果 `.context/` 被忽略，明确告诉用户文件只保留在本地。

用户要求更新腾讯任务表时：

- 先重新读取实时工作表、表头和目标行。
- 将共享状态与用户旅程的任务合并；将被合并旧行标记为现有的“不再追踪”状态并写明去向。
- 保留独立的长期资源任务，不强行塞进功能任务。
- 对三个及以上单元格使用一次批量写入。
- 写入后回读所有目标行，并执行可用的数据校验。

## 7. 完成判定

只有同时满足以下条件，才称需求“可直接开发”：

- 没有会改变架构或用户体验的未决问题。
- 代码入口和主要依赖已确认，不靠猜测 API。
- 范围与非目标明确。
- 边界情况有处理规则。
- 验收标准可操作。
- AI 能完成的部分与需要用户实机验证的部分已经分开。
- 后续会话能够仅凭规格文件或任务详情开始工作。

结束时给出清晰状态：哪些已就绪、哪些仍阻塞、用户下一步只需做什么。不要在需求梳理完成后擅自开始编码。
